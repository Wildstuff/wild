# Configuration Variables — Canonical Inventory

This document is the single source of truth for every environment
variable read by Wild's runtime. It exists to satisfy ADR 0004
(Configuration Injection): every variable here either flows through
`wild_runtime::RuntimeConfig` or is explicitly excluded.

**Rule:** new code must not call `std::env::var("WILD_…")` outside
`crates/runtime/wild-runtime/src/config.rs`. The CI lockdown step
(see `.github/workflows/ci.yml`) enforces this.

## Section 1 — `WILD_*` application configuration (flows through `RuntimeConfig`)

These vars map onto fields of `wild_runtime::RuntimeConfig` (or one
of its sub-structs). Production code reads the field, not the env.
Tests construct `RuntimeConfig::for_test_with(|c| …)` overrides.

| Env var | Default | Config field | Sub-struct | Semantics |
|---|---|---|---|---|
| `WILD_NATS_URL` | `nats://127.0.0.1:4222` | `cfg.nats.url` | `NatsConfig` | NATS broker the host connects to. On the CLI side it is rung 2 of the one resolution ladder every verb shares (`cli_config::resolve_nats_url`): `--nats-url` flag > this var > `<wild_root>/cli.toml` `nats_url` > the resolved profile's `profile.yaml::nats_url` > the built-in default. The daemon (`wild-hostd`) runs the same ladder minus the cli.toml rungs — ADR-0009 §4 makes cli.toml client-owned. |
| `WILD_MESSAGING_ALLOWLIST_ENFORCE` | unset (false) | `cfg.nats.allowlist_enforce` | `NatsConfig` | ADR-0062 (one gate) — posture of the guest-publish **capability allowlist** check. Every deploy stamps the rendered per-role publish allowlist (`build_allowlist`, the same render the subscribe wiring reads) onto the component config (`wild/publish-allowlist`); the messaging plugin's publish ACL evaluates it INSIDE the tenant scope. Default (unset/`0`) = **shadow**: an in-tribe publish outside the role's allowlist is allowed with one WARN naming the miss. `1`/`true` = **enforce**: an allowlist miss denies the publish. The e2e fixture suite (`xtask tribe-e2e`) runs with `WILD_MESSAGING_ALLOWLIST_ENFORCE=1` so every merge proves the rendered allowlists cover the fan-out architecture's real publishes; the default remains shadow for existing operator installs until a separate one-line flip PR is approved. Cross-tribe publishes are denied in BOTH modes (the tenant scope is the sovereign outer bound; a stamped allowlist can only narrow inside it). Components deployed by an older plan without the stamp keep the tenant-scope-only behaviour. |
| `WILD_OCI_REGISTRY` | `ghcr.io/wildstuff` | `cfg.oci.prefix` | `OciConfig` | OCI registry prefix for image pulls — and, when set explicitly, the best-effort **mirror** for forge-built artifacts. Since ADR-0260 D10 the canonical publish target is always the local store (`<profile_root>/forge/store/`); an explicit registry here is mirrored to after the store write, and a mirror failure degrades to a WARN event, never `publish-failed`. Set to a local registry (e.g. `localhost:5000/wildstuff`) for dev round-trips without `ghcr.io`; `local`/`none`/`off` (or unset) = store only. |
| `WILD_OCI_TAG` | `0.1.0` | `cfg.oci.tag` | `OciConfig` | Default tag suffix when manifests reference unversioned images. |
| `WILD_HOME` | `wild_root()` — platform-resolved | `cfg.home` | (top-level) | Wild root directory. The default is whatever `wild_core::user_dirs::wild_root()` returns for the platform (macOS `~/Library/Application Support/Wild`, Linux `$XDG_DATA_HOME/wild` else `~/.local/share/wild`, Windows `%LOCALAPPDATA%\Wild`) — see `profile-layout.md` § Where the root is. Setting this overrides the resolver everywhere, which is what test/fixture isolation needs. CLI overrides it at boot with the profile-resolved path; `wild-hostd` uses the default. |
| `WILD_PROFILE` | `default` | `cfg.identity.profile` | `IdentityConfig` | Active profile name. Decided once at boot — switching profiles requires a restart per ADR-0004 §Phase 0. |
| `WILD_TENANT` | `local` | `cfg.forge.tenant` | `ForgeConfig` | Forge build-context tenancy label. |
| `WILD_RBAC_ENABLED` | unset (false) | `cfg.rbac.enabled` | `RbacConfig` | Role-based access control over decision proposals. **Off by default** — the host-asserted `actor` is carried but never consulted, so behaviour is byte-near the single-operator system. When `1`/`true`, the decisions gate enforces a role×risk matrix on human-attributed proposals; system / internal / cron actions stay governed by the autonomy gate. **Also settable per-profile via `profile.yaml` `rbac:` (ADR-0050)** — this env var, when explicitly set, WINS over the profile value. |
| `WILD_FORGE_BACKEND` | `remote` | `cfg.forge.backend` | `ForgeConfig` | Which build backend the daemon wires at boot (ADR-0260 D4): `docker` (local sandbox container) or `remote` (builds submitted to a `wild-forged` service — nothing container-shaped runs locally). An unrecognized token FAILS the boot by name instead of silently falling back. The default is `remote` (ADR-0260 D2 — the hosted builder is what an operator install gets by saying nothing); `docker` stays selectable and no code was removed, so an install without network, or one that wants builds to stay on its own machine, keeps a working path. |
| `WILD_FORGE_BUILDER_URL` | `https://forge-eu.wildstuff.com` | `cfg.forge.builder_url` | `ForgeConfig` | `wild-forged` builder base URL (ADR-0260 D7), e.g. `https://builder.example:8443`. Defaults to the HOSTED builder, so the `remote` default backend has a working target without any configuration — a default that only works after the operator sets a variable is not a default. Set it to point at your own `wild-forged` (self-hosted or a local cluster). Ignored by `docker`. The compiled-in value names a host whose DNS we control, so moving the service is a DNS change rather than a release. Constructing the config directly with `None` still boots DEGRADED (readiness names the gap; every build refuses with the same message). Deliberately no companion token variable — ADR-0260 D8 signs requests with the install keypair, so no bearer secret exists. |
| `WILD_FORGE_RECEIPT_VERIFYING_KEY` | unset (shipped hosted-builder key) | `cfg.forge.receipt_verifying_key` | `ForgeConfig` | ADR-0267 D7 — the Ed25519 public key (64 hex) build receipts must verify under. Unset = the hosted builder's shipped key (a pre-hosted-launch placeholder constant until that service exists); a self-hosted `wild-forged` sets this to ITS receipt key (the server logs it at startup when `WILD_FORGED_RECEIPT_KEY` is configured). Only meaningful with the `remote` backend. A PRESENT receipt that fails this key fails the build as tampered; an ABSENT receipt is accepted pre-launch. An unparsable value warns and keeps the shipped default — verification never switches off. Daemon-side root→certificate chain verification is the named ADR-0267 D9 residual (the build response does not carry the certificate yet); until it lands this pin is the operator's trust statement for a self-hosted builder. |
| `WILD_FORGE_MAX_PARALLEL` | `1` | `cfg.forge.max_parallel` | `ForgeConfig` | Cap on simultaneous builds (all share one sandbox container). Raising it also scales the container memory (`PoolConfig::with_concurrency`). `0` = no cap. **Also settable per-profile via `profile.yaml` `forge_max_parallel:`** — this env var, when explicitly set, WINS over the profile value. |
| `WILD_FORGE_MAX_QUEUE` | `4` | `cfg.forge.max_queue` | `ForgeConfig` | ADR-0073 D8′ — how many builds may WAIT for a slot before a submit is refused with `forge-queue-full`. Bounds the backlog, not the wait: an admitted waiter's ceiling is derived from `WILD_FORGE_WALL_TIMEOUT_SECONDS` and its queue position, so it outlives the build ahead of it instead of dying at a flat timeout. The default is half the bus dispatch pool (`wild_core::dispatch_budget`) because a waiting build holds a dispatch slot — raise it only alongside `WILD_FORGE_MAX_PARALLEL`, or forge saturation becomes bus saturation. Read the live depth with the `forge_capacity` tool. |
| `WILD_FORGE_DISK_MB` | `500` | `cfg.forge.disk_mb` | `ForgeConfig` | Sandbox tmpfs ceiling per build. |
| `WILD_FORGE_IDLE_TIMEOUT_SECONDS` | `600` | `cfg.forge.idle_timeout_secs` | `ForgeConfig` | Container kill timer when build emits no output. |
| `WILD_FORGE_WALL_TIMEOUT_SECONDS` | `300` | `cfg.forge.wall_timeout_secs` | `ForgeConfig` | Hard ceiling per build regardless of progress. The wall-timeout < idle-timeout asymmetry is deliberate (see `config.rs` `DEFAULT_FORGE_*` + `forge/src/docker.rs`). |
| `WILD_FORGE_FAIL_THRESHOLD` | `3` | `cfg.forge.fail_threshold` | `ForgeConfig` | Build retries before escalation. |
| `WILD_FORGE_REQUESTOR` | `user-direct` | `cfg.forge.requestor` | `ForgeConfig` | Build-request identity attached to forge handler events. |
| `WILD_FORGE_SANDBOX_IMAGE` | `ghcr.io/wildstuff/forge-sandbox:0.3.0` | `cfg.forge.sandbox_image` | `ForgeConfig` | Docker image the forge handler spawns per build. The default is a REGISTRY reference, not a local tag: the daemon pulls it on the first forge build if absent (`forge/src/docker.rs`), so the package must be anonymously pullable or forging fails for every install outside the publishing org. The documented default said `forge-sandbox:latest` until 2026-07-31 — a purely local tag, which would never pull at all; corrected against `DEFAULT_FORGE_SANDBOX_IMAGE`. Verified by `xtask verify-pinned-images`, which reads this const rather than trusting the table. |
| `WILD_MCP_BIND` | `127.0.0.1:7531` | `cfg.mcp.bind` | `McpConfig` | TCP bind address for the MCP HTTP gateway. An explicitly-set value (this env or `--mcp-http`) is **required**: a failed bind — e.g. another daemon already holds the port — aborts boot with a non-zero exit (issue #3196); only the plain `profile.mcp_port` fallback degrades to a WARN on failure. |
| `WILD_MCP_ALLOW_EXTERNAL` | `false` | `cfg.mcp.allow_external` | `McpConfig` | HALF of the deliberate two-step opt-in to bind the MCP operator plane to a **non-loopback** address. Default off ⇒ a `--mcp-http-bind 0.0.0.0` (or any non-loopback `WILD_MCP_BIND`) is **refused** before the listener starts — the MCP surface serves the full ~161-tool operator catalog, so a single accidental external bind must not expose it. Per ADR-0050 §7 Amendment (2026-08-18, second) this flag ALONE no longer lifts the refusal (**breaking** for pre-amendment `=1` deployments): the non-loopback bind ALSO requires the inbound TLS identity (`WILD_TLS_CERT` + `WILD_TLS_KEY`) to yield a constructible acceptor at arm time, and the listener then serves TLS — the old boot WARN ("front-load TLS at your gateway") is retired with the hole it apologised for. Migration: add the identity, or drop to a loopback bind behind an SSH tunnel. The bearer token still authenticates every request. Twin: `WILD_REST_ALLOW_EXTERNAL`. |
| `WILD_REST_BIND` | unset → profile `rest_port` → **off** | `rest_bind_from_env()` | (free fn) | ADR-0050 V1 — explicit override for the REST **HTTP(S)** control/query listener bind (a plain TCP port carrying ordinary HTTP — an nginx/Caddy/any reverse proxy fronts it like any web upstream) (`--rest-http` has the same effect). **P3c — the network listener is OFF by default**: the chain is `--rest-http` → this env → profile `rest_port`, with **no default fallback**; if all are unset the HTTP door stays down and the operator plane serves over the Unix socket (`<profile>/system/api.sock`). Set this (or `rest_port`, e.g. `127.0.0.1:7532`) to open TCP for the browser dashboard, or as the local end of an SSH tunnel to a remote daemon (`docs/operator-daemon.md` § Reaching a remote daemon). **The operator plane is loopback-only by default** — a non-loopback bind is refused unless the ADR-0050 §7 Amendment (2026-08-18, second) precondition is met: `WILD_REST_ALLOW_EXTERNAL=1` AND the inbound TLS identity (`WILD_TLS_CERT` + `WILD_TLS_KEY`) yields a constructible acceptor — the listener then serves TLS (loopback binds stay plaintext; the Unix socket is untouched). The former "one all-powerful bearer" ground was struck earlier: `wild user` mints scoped, rotatable, revocable credentials and `rest_http::scope_decision` enforces the tribe scope with RBAC off, so the RBAC rollout is NOT a precondition for external exposure. Customer-facing external binding remains the ADR-0083 PR5a customer listener's job (`WILD_CUSTOMER_BIND`). |
| `WILD_REST_ALLOW_EXTERNAL` | `false` | `rest_allow_external_from_env()` | (free fn) | ADR-0050 §7 Amendment (2026-08-18, second) — the REST operator door's twin of `WILD_MCP_ALLOW_EXTERNAL`: HALF of the deliberate two-step opt-in for a non-loopback `WILD_REST_BIND`. On its own it lifts nothing — the bind ALSO requires the inbound TLS identity, and the listener then serves TLS. Ignored by the customer listener (its exemption is structural, not flagged). |
| `WILD_TLS_CERT` | unset | `InboundTlsConfig::cert` | `InboundTlsConfig` | ADR-0050 §7 Amendment (2026-08-18, second) — PEM certificate-chain path of the daemon's **inbound** TLS identity, one identity consumed by BOTH operator doors (REST + MCP). Required (with `WILD_TLS_KEY`) for any non-loopback operator bind; the check is the TLS acceptor **successfully constructing** from the pair at arm time — a garbage PEM fails the arm synchronously with the path named. Set without `WILD_TLS_KEY` ⇒ boot refuses (a half-set identity is a config lie). Loopback binds and the Unix socket stay plaintext. Rotation = daemon restart; certificate lifecycle (ACME, renewal, auto-generation) is deliberately out of scope (own ADR when wanted). A cross-container reverse proxy dials this daemon over TLS too — a self-signed identity suffices for that hop. |
| `WILD_TLS_KEY` | unset | `InboundTlsConfig::key` | `InboundTlsConfig` | PEM private-key path of the inbound TLS identity — pair of `WILD_TLS_CERT`, same rules (both or neither; constructibility checked at arm time). |
| `WILD_CUSTOMER_BIND` | unset → no customer surface | `customer_bind_from_env()` | (free fn) | ADR-0083 PR5a — bind for the in-process CUSTOMER REST listener (`--customer-http` has the same effect). **OPT-IN, no default** — absent ⇒ no customer surface. ### wild-forged server (`WILD_FORGED_*`, standalone binary)

ADR-0260 — the `wild-forged` build server reads these through its own
self-contained config module (`forged/server/src/config.rs`, on the
env-lockdown allowlist — same pattern as `wild-appd`). It deliberately
links none of the daemon graph, so nothing here flows through
`RuntimeConfig`.

### Skip-flags policy

`WILD_SKIP_*` flags exist for development and integration testing.
In **release builds**, `RuntimeConfig::from_env` logs a warning at
boot when any skip-flag is set, but honours the flag (staging
environments routinely use release builds with skips). The warning
makes accidental production use visible in logs.

### Profile lifecycle

`WILD_PROFILE` is read once at process boot (per ADR 0004 §Phase 0
decision). Profile switching requires a restart. A future ADR can
introduce hot-reload via `Arc<RwLock<RuntimeConfig>>` if the
product needs live profile-swap.

## Section 2 — OS-interface vars (stay direct, never enter `RuntimeConfig`)

These are standard OS contracts. They are read at point-of-use
because the OS is the source of truth, not Wild's config. Wrapping
them in `RuntimeConfig` would force tests to inject identity
plumbing for no payoff.

| Env var | Read by | Purpose |
|---|---|---|
| `HOME` | many | OS user home; falls back when `WILD_HOME` is unset. |
| `PATH` | `nats.rs`, `claude_cli.rs`, `doctor.rs`, `hostd_supervisor.rs` | Binary discovery (nats-server, claude). |
| `USER` | `config.rs` (home fallback), `plugin.rs` / `plugin_provision.rs` (`added_by`) | Tags the degenerate `$WILD_HOME`/`$HOME`-unset temp root (`/tmp/.wild-<user>`) and stamps the `added_by` provisioning field. |

logs through, so they cannot flow through the struct. Same pattern
as `RUST_BACKTRACE`. Full operator how-to: `docs/observability.md`.

|---|---|---|
| `WILD_LOG_FORMAT` | `pretty` | stderr render mode: `pretty`, `json`, `compact`. |

`WILD_NATS_TOKEN` is why `nats.conf` carries no secret: the
`authorization` block references the var, the conf stays shareable, and
token rotation only rewrites `system/token` (the next broker start picks
it up). Mechanism works identically on macOS/Linux/Windows — nats-server
does the expansion itself.

`GITHUB_TOKEN` is intentionally read at point-of-use — it's an auth
secret pulled fresh per network call, not declarative config.

`WILD_TOKEN` is the same class: stage 1 of the shared HTTP bearer-token
resolution (`wild-shared/src/auth.rs::resolve_token` — env wins over the
on-disk `system/token` file, which is created on the fly when both are
absent). ONE secret for both transports (MCP + REST). An auth secret, not
declarative config; the env-var name reaches `env::var` through a parameter
so parallel tests can use scratch names. (Renamed from `WILD_MCP_TOKEN` /
`system/mcp.token` — no env alias; the file is migrated on first resolve.)

## Allowed env-reading sites (post-refactor)

The CI lockdown step in `.github/workflows/ci.yml` rejects any
`std::env::var("WILD_…")` outside this allowlist:

| File | Reason |
|---|---|
| `crates/runtime/wild-runtime/src/config.rs` | canonical `RuntimeConfig::from_env` + sub-struct parsers |
| `crates/runtime/shared/src/wild_home.rs` | wild-home-dir resolver — `WILD_HOME` override for the profile-resolved root (moved here from the `cli` crate by ADR-0036 Phase A) |
| `crates/runtime/shared/src/log_setup.rs` | tracing/log init — also moved into `wild-shared` by ADR-0036 Phase A |
| `crates/xtask/src/dev.rs` | xtask's `WILD_OUTPUT=raw` opt-out for the phased renderer + the `WILD_PROFILE` sidecar-install target |
| `crates/xtask/src/e2e.rs` | xtask's `tribe-e2e` runner reads `WILD_BIN` — the suite-scoped `wild` binary-path override (same one `tests/e2e/tribes/_lib.sh` honours) — to skip its pre-run release build when the operator points at a specific binary |
| `crates/xtask/src/worktree_init.rs` | the per-worktree isolation bootstrap's four dev-loop knobs (`WILD_PERWORKTREE_TARGET`, `WILD_USE_KACHE`, `WILD_USE_SCCACHE`, `WILD_AGENT_FLEET_SIZE`). They shape one developer's build cache before any Wild process exists, so there is no `RuntimeConfig` to route them through — they were bash `${VAR:-}` reads in `scripts/worktree-init.sh` until that logic moved into Rust |

Test code (anything under `mod tests {` in a source file, plus
files under `tests/` and `benches/`) is exempt. The lockdown also
allows `set_var`/`remove_var` in three subprocess-spawn helpers
(`attach.rs`, `elder.rs`, `hostd_supervisor.rs`) where env IS the
right interface for crafting a child's environment.

## How to add a new tunable

1. Add the env name to Section 1 with default + target Config field.
2. Add the Rust field to the appropriate sub-struct in
   `wild-runtime/src/config.rs`.
3. Read the env in that sub-struct's `from_env`.
4. Pass the field into the consuming subsystem via a constructor arg.
5. Reference the new field from this doc.

Do **not**:
- Add a `std::env::var("WILD_…")` call outside `wild-runtime/src/config*.rs`.
- Add a `set_var`/`remove_var` call to non-test code.

## ADR-0165 note

The field-level LLM privacy-scope feature (`llm_scope` / `privacy_tier`)
introduces **no new `WILD_*` environment variable**. Adapter classification
is YAML-only (`llm-adapters.yaml`, `embed-adapters.yaml`,
`mcp-servers.yaml`); the runtime derives every data-membrane decision from
those declarations.
